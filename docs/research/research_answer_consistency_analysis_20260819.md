# 研究報告：Antigravity 與 Web 端針對相同問題回答差異之根本原因與一致性解決方案

**研究時間**: `2026-08-19 09:56:28`  
**比對問題**: `請給我一個PBHA IP Quorum設定的建議如果我的兩個FS5600系統放在兩個不同的site IP Quorum該怎麼設計`  
**核心目標**: 找出 IDE/Antigravity 與 Web Portal 輸出風格與內容結構差異的底層原因，並提出統一且一致的架構解決方案。

---

## 🔬 一、兩者回答的核心差異對比 (Side-by-Side Comparison)

| 評估維度 | Antigravity (IDE 專家模式) | Web Portal (當前網頁端輸出) | 差異根本原因 |
| :--- | :--- | :--- | :--- |
| **1. 輸出篇幅** | 精煉適中（約 1,200 字） | 萬字長篇（高達 11,000+ 字） | Web 端觸發了 Tier 4「三章節並行鏈式管線」，而 IDE 採用了單次精煉問答。 |

## 🔍 二、底層技術成因深入分析 (Deep Root Cause)

### 1. 意圖分類觸發過度敏感 (Intent Over-Triggering)
* 在先前解決截斷問題時，我們將 `["設計", "建議", "site", "雙站點"]` 等詞彙加入了 `tier4_architecture`。
* 這導致使用者的諮詢問題只要帶有「建議」或「設計」，就會被強制啟動 **Tier 4 萬字並行鏈式生成 (`_execute_chained_generation`)**。
* 事實上，使用者的需求是「清晰、精準、直接可用的 IP Quorum 設計建議」，而不是三萬字的端到端遷移工程。

### 2. 鏈式管線缺少「去客套與防重疊」指令約束
* 在 `_execute_chained_generation` 中，三個子章節 Prompt 各自獨立運行：
  - 子章節 1 講了延遲 80ms、Port 1260；
  - 子章節 2 又重新列出延遲 80ms、Port 1260、java -jar；
  - 子章節 3 又再次重複延遲 80ms、Port 1260。
* 這造成了技術資訊的反覆堆疊與 3 次重複自我介紹。

---

## 💡 三、達成兩端答案 100% 一致的解決方案 (Proposed Solution)

### 方案 A：校準意圖分流（將諮詢類回歸高質感單次生成）
1. **Tier 4 僅保留給真正的「端到端遷移與重大升級工程」**：
   * 觸發關鍵字精確鎖定為：`["轉換為", "轉換成", "遷移至", "遷移到", "升級流程", "實施計畫", "實施流程", "從傳統"]`。
2. **架構規劃與諮詢（包含 PBHA、IP Quorum 設計、雙站點建議）**：
   * 分流至 **Tier 2 (規格與架構諮詢服務)**。
   * 因為我們已經在 `_call_gemini_api` 導入了 `thinkingBudget: 1024` 與 `Auto-Continue`，**Tier 2 現在已擁有高達 7,000+ Tokens 的超大正文容量，且 100% 不會被截斷**！
   * 輸出將與 Antigravity IDE 一模一樣：結構極度乾淨、層次分明、無重複客套話。

### 方案 B：優化 Tier 4 鏈式管線（若遇到真正的遷移工程）
1. **子章節 Prompt 強制去客套話**：
   * 明確要求大模型：`禁止輸出任何自我介紹、客套開場白或收尾客套話，直接從章節標題開始輸出核心技術正文。`
2. **章節邊界明確化**：
   * 第一章專注「架構原理與前置」；第二章專注「CLI 指令與操作步驟」；第三章專注「狀態監控與驗證」，嚴禁跨章節重複敘述相同參數。
