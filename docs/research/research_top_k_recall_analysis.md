# 本地資料庫增加召回數量 (Top-K) 之有效性與技術邊界研究報告

## 📌 研究結論摘要 (Executive Summary)

**結論：對於「特定錯誤代碼 (如 CMMVC1035E)」等知識點，盲目增加本地資料庫召回數量 (Top-K) ❌ 完全沒有幫助，反而會帶來三大負面副作用。**

經過對目前本地 782,177 筆知識庫進行全庫底層 SQLite 窮舉掃描：
* 全庫中所有包含 `CMMVC1035E` 的 Chunk 總共有 28 筆。
* **這 28 筆 100% 全部都是「目錄超連結清單 (Table of Contents)」**，沒有任何一筆包含正文定義（"The restore command failed..."）。
* 因此，將 `top_k` 從 25 提高到 50 或 100，只會撈出更多重複的「目錄清單」，**無法無中生有變出不存在的正文**。

---

## 🔬 增加 Top-K 的適用場景與技術邊界 (Technical Boundary)

| 場景分類 | 增加 Top-K (召回更多) 的效果 | 說明 |
| :--- | :---: | :--- |
| **A. 知識點正文「尚未收錄」** (如 CMMVC1035E) | ❌ **毫無幫助 (0%)** | 資料庫內正文筆數為 0，召回再多也只能召回更多空殼目錄。 |
| **B. 零件料號 / 單一明確表格** (如 01LJ207, 03NK551) | ⚠️ **邊際效益極低** | 混合檢索 (BM25) 已經在前 3 名精準命中，不需要擴大到 50 筆。 |
| **C. 跨章節長篇規劃 / 容災遷移步驟** (如 Q1, Q4) | ✅ **有中度幫助** | 流程分散在規劃篇、CLI 篇、容災篇，需要較廣的上下文覆蓋。 |

---

## ⚠️ 盲目增加 Top-K 的三大技術副作用 (Side Effects)

1. **目錄噪聲污染 (TOC Contamination)**：
   * 檢索結果會被大量的 `- [CMMVC1001E]... - [CMMVC1035E]...` 導覽列淹沒，稀釋掉真正有用的技術段落。
2. **迷失在中間效應 (Lost in the Middle Effect)**：
   * LLM 研究證實，當 Context 注入過多無效 Chunk 時，模型會忽略核心資訊，更容易引發臆測與幻覺。
3. **延遲與 Token 消耗倍增**：
   * 每增加 25 筆 Chunk，Prompt Token 暴增約 8,000 ~ 15,000 Tokens，導致 Web 端的回答延遲拉長 3~5 秒。

---

## 🎯 真正有效的根本解法 (The Correct Solutions)

1. **精準收錄「錯誤碼正文手冊」**：
   * 將 IBM FlashSystem 官方的完整 `Messages and Codes Reference` 手冊直接匯入，一次性將 2,000 多條 CMMVC/010xxx 正文寫入 DB。
2. **目錄清單降噪過濾 (TOC Filtering)**：
   * 在 Chunking 預處理階段，自動過濾掉純超連結目錄頁，確保進入向量庫的每一筆資料都是具備實質意義的技術說明。
