# 研究報告：如何徹底杜絕專家系統產生 LLM 自行推測（幻覺），確保 100% 嚴格忠於權威資料來源

**研究時間**: 2026-08-20 12:37:49  
**核心問題**: 針對先前「大模型自行推論出看似合理、卻違背原廠硬性前置限制 (Pre-upgrade Blocker) 的假想方案」，制定出能從**提示詞約束、檢索增強、負向約束、真實性驗證過濾器 (Fact-Checking Filter) 與拒絕機制**等多維度防護體系。

---

## 🔬 一、為什麼大模型會「自作聰明」產生未經證實的推論？（根本機理）

在 RAG 系統中，大模型產生未記載推論（Extrapolative Hallucination / 延伸性幻覺）的核心原因如下：

1. **過度取悅與泛化推理 (Over-helpful Extrapolation)**：
   * 當提問包含「有沒有更好的辦法？」或「如何縮短停機時間？」時，LLM 的底層訓練傾向於扮演「無所不能的顧問」，自動組合分散的知識（如：知曉 9.1 支援 PBR，又知曉 3-Site，便擅自拼湊出「先升級再抄寫」的過渡流程），而忽略了兩個技術點之間的「硬性不相容前置限制」。
2. **缺乏「不可推測宣告」與「嚴格錨定 (Strict Grounding)」約束**：
   * 原先的提示詞雖然要求「依據參考資料」，但未明確告知模型：**「嚴禁自行創造未經紅皮書明確記載的過渡方案或升級路徑。凡是無直接出處支持的步驟，必須明確聲明『未在官方資料中記載』或直接拒絕推測！」**
3. **缺少事後事實交叉檢驗機制 (Fact Verification Gate)**：
   * 輸出的每一句話如果沒有在提供的 Context 找到直接對應的頁碼依據，未被即時過濾或標註警示。

## 🛡️ 二、四重防護體系：打造 100% 零臆測的「原廠鐵律 RAG」

### 1. 第一重：溫度係數收斂至零 (temperature: 0.0)
* **原理**：將 temperature 從 0.2 調降至 0.0（完全確定性 Greedy Decoding）。
* **效果**：徹底關閉大模型的發散創造力，強制其僅選擇機率最高、與參考 Context 最相符的字詞輸出。

### 2. 第二重：注入「原廠鐵律」負向約束 (Negative Prompt Constraints)
在 prompts.py 的中央提示詞中，寫入具備法律級約束力的指令：
- 嚴禁任何自由發揮或邏輯拼湊：答案中的每一個架構步驟、升級路徑與參數限制，必須在【參考技術資料】中具有明確、逐字對應的原文依據。
- 嚴禁自行創造「替代過渡方案」：若參考資料中未明確記載某種升級過渡方式，絕對禁止憑空推論「可以先做 A 再做 B」，必須明確回答：「IBM 官方參考手冊未記載此過渡方式，唯一官方認證步驟為...」。
- 嚴禁無來源的建議：任何未附帶 [來源: 文檔.pdf, 第 X 頁] 的技術步驟，視為無效內容，禁止輸出。

### 3. 第三重：多輪追問與「有沒有更好辦法」的專屬防禦
當使用者問「有沒有更好辦法」或「能不能這樣做」時，明確要求模型：
- 只能從參考資料中已記載的官方替代方案（如：官方明確列出的 Option A / Option B）中挑選回答；若資料中只有唯一標準做法，必須明確告知客戶『官方僅提供此單一標準實施路徑，無其他未經認證之旁門做法』。

### 4. 第四重：事後出處完整度檢驗 (Post-generation Citation Gate)
- 在後端 rag_core.py 檢查：若模型輸出的建議中，包含未帶有 [來源: 標籤的自創章節或虛構指令，系統自動觸發告警或在文末自動附加提示。

## 📊 三、預期改善效益與對比

- 問：「HyperSwap 轉 PBHA 有沒有更好的辦法縮短停機？」
- 原先：模型為了討好使用者，自行腦補「先升級 9.1 再抄寫」的虛構過渡方案。
- 改善後：模型嚴格回答：「經檢索官方紅皮書，IBM 官方對於 HyperSwap 轉 PBHA 僅記載了標準的拆解 -> 升級 -> 重新建立 PBHA 這一條認證路徑。官方資料中未記載任何可保留 HyperSwap 直升 9.1 的過渡做法（且 9.1 已正式終止支援 HyperSwap 拓撲），因此不建議採用任何未經原廠認證的推測流程。」
