架構與工程技術說明文件 (Explanation Workpage)

IBM FlashSystem 專家系統與 RAG 架構

完全本地化多模態 RAG 管道、Vision 圖表解析、向量引擎與 MCP Server 整合

1

這是在做什麼 (What is this)

本專案是一個完全本地化、多模態的檢索增強生成 (RAG) 專家系統，專為 IBM FlashSystem 儲存陣列（包含 FS5000, FS5200, FS5600, FS7300, FS9500 與 SVC 2145 等）打造。系統自動解析 48+ 本 IBM 紅皮書 (PDF)，透過 Ollama llama3.2-vision 多模態模型自動辨識 SAN 拓撲與 RAID 架構圖，使用 Playwright 遞迴爬取 IBM Docs 單頁應用 (SPA)，並透過標準化 Model Context Protocol (MCP) 介面提供給自主 AI Agent 直接調用。

Python 3.12 ChromaDB 本機向量庫 Ollama (Nomic-Embed & Vision) FastMCP / MCP 2.0 Playwright SPA 爬蟲 PyMuPDF 圖表提取
2

為什麼選擇此架構 (Why this approach)

權衡比較 「本機離線 RAG + MCP Server」 方案與 「純雲端 LLM API」 及 「人工手動查詢」 的技術指標與效益。

架構評估維度 本專案採用：本機 RAG + MCP Server 替代方案：純雲端 LLM API 替代方案：傳統人工手動檢索
資料安全與隱私 ✓ 100% 離線隱私（內部 SAN 拓撲零外洩） ✘ 存在資安風險（內部 IP 與設定上傳至雲端） ✓ 安全（人工閱讀）
營運成本結構 ✓ $0 運算費用（本地硬體推理） ✘ 按 Token 計費（7萬+ Chunks 費用昂貴） ✘ 高昂人力成本（耗費數小時查閱紅皮書）
AI Agent 工具整合 ✓ 標準化 MCP（對話框一鍵 @調用） △ 須客製 API Plumbing ✘ 無法與 AI 整合
多模態技術圖表理解 ✓ 自動 Vision OCR（Ollama 生成繁中圖表摘要） △ Vision Token 費用極高 ✘ 僅靠人工肉眼辨識

什麼情況會出錯 (What would break / 系統依賴與風險)

系統依賴拓撲與潛在故障模式（含嚴重點列與防呆解決方案）。

  • [警告] SQLite 檔案鎖定危機： 若向量庫路徑放置在 Google Drive 同步資料夾內，背景同步會在批次寫入時鎖定 chroma.sqlite3。解決方案：將持久化目錄隔離移至本機家目錄 ~/.ibm_flashsystem_kb/。
  • [提示] MCP SDK 異動破壞： mcp 2.0 套件重構了 FastMCP 模組導出路徑。解決方案：實作 try...except ModuleNotFoundError 雙重 fallback 相容導入。
  • [嚴重] 缺少的 Quorum 在線更換風險： 進行 SVC 2145-SV1 至 SV3 節點更換時，若 Active Quorum 磁碟異常，會引發 Cluster 防腦裂 Panic。解決方案：強迫執行前置 lsquorum 檢查與 30 分鐘快取同步觀察期。
4

從中學到了什麼 (What I learned)

  • 本機資料庫與雲端同步資料夾必須隔離
    切勿將基於 SQLite 的向量資料庫 (ChromaDB) 直接放在 Google Drive 或 OneDrive 資料夾內。背景同步進程會干擾 HNSW Compaction 與 SQLite WAL 寫入；將路徑隔離至本機 ~/.ibm_flashsystem_kb/ 可確保極致穩定的寫入效能。
  • 具備彈性防禦的 MCP SDK 相容性設計
    快速迭代的 AI Protocol (MCP) 經常變更內部導出名稱。採用 Python try...except ModuleNotFoundError 的相容包裝模式，能讓工具伺服器在舊版與新版 MCP 2.0 套件下皆可無縫啟動，避免 Agent 開啟時伺服器崩潰。
  • 企業級 SAN 維護與在線移轉的防呆嚴謹度
    在進行高風險的硬體更換工程（如 SVC 2145-SV1 到 SV3 在線替換）時，必須嚴格執行三道防線：事前 lsquorum 驗證、接光纖前寫入 VPD FC Port Map、以及每個節點替換完成後停留 15~30 分鐘確認快取同步。
